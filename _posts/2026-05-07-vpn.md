# 第八章：VPN

> 你在一个不安全的网络上（公共 Wi-Fi、不可信 ISP），但你需要像在自己家里一样安全地访问网络资源。VPN 把整台设备的所有流量装进一条加密隧道，送到一个你信任的端点，由它帮你转发。

## 问题 0：TLS 已经有了，为什么还需要 VPN？

第七章讲了 TLS——HTTPS 已经加密了网页内容。那 VPN 还加密什么？

**TLS 只保护了 HTTP 的内容，但没保护"你跟谁在说话"。**

```
你在咖啡店访问 https://www.baidu.com：

TLS 保护的：
  你发了什么搜索词       → 加密 ✓  偷听者看不到
  百度回了什么结果       → 加密 ✓  偷听者看不到
  你的密码 / Cookie     → 加密 ✓  偷听者看不到

TLS **没**保护的：
  你访问了 110.242.68.66           → IP 头是明的，所有人都能看到
  DNS 查询"www.baidu.com 的 IP"    → 明文可见（如果 DNS 没走加密）
  你在微信上发消息（不走 HTTP）      → 微信有自己的加密，但目的 IP 暴露
  你在用 BT 下载                    → ISP 看到大量 P2P 连接

更根本的问题：
  咖啡店 Wi-Fi 管理员看到：你的 MAC → 你的 IP → 目的 IP → 端口
  → 虽然看不到内容，但知道"你在浏览百度""你在看抖音""你在连微信"
  → 这叫**元数据泄漏**——跟谁、什么时候、多少流量，这些本身就是情报
```

**TLS 和 VPN 的根本区别**：

| | TLS (HTTPS) | VPN |
|---|---|---|
| 保护范围 | 一个应用（浏览器）的 HTTP 流量 | 整台设备的所有流量 |
| 保护的层 | 应用层（HTTP 内容） | 网络层及以上的**所有**数据 |
| 谁能看到目的 IP | 中间路由器、ISP 都能 | 只有 VPN 服务器能（ISP 只看到 VPN 服务器的 IP） |
| 元数据 | 暴露（哪个 IP、什么时候、多少流量） | 对 ISP 隐藏（只看到你在跟 VPN 服务器通信） |
| 适用的应用 | 只浏览器（HTTPS） | 所有应用（浏览器、微信、游戏、终端...） |

> TLS 保护的是"**你说了什么**"。VPN 保护的是"**你跟谁说了话，以及你说了什么**"。

## 问题 1：VPN 本质上是什么？——"加密隧道"的物理直觉

不需要任何协议知识，用物理直觉理解 VPN：

```
没有 VPN 时：

你的电脑 ──────── 互联网（公开的） ──────── 目标服务器
         你的包：                              收到的包：
         源 IP = 你的真实 IP                    源 IP = 你的真实 IP
         目的 IP = 目标 IP                     知道你从哪来
         内容 = 加密或明文                      知道你访问了什么


有了 VPN 时：

你的电脑 ═══ 加密隧道 ═══ VPN 服务器 ─── 互联网 ─── 目标服务器
          │                │                       │
         源 = 你          解包后重新封装：          收到的包：
         目的 = VPN        源 = VPN 服务器的 IP     源 IP = VPN 服务器
         内容 = 加密       目的 = 目标 IP           不知道真正的你从哪来
                           转发了你的包
```

**VPN 做的事情本质上只有一件**：

> 把你的整个 IP 包（或以太网帧）原封不动地加密，装进另一个 IP 包的"数据"部分，发到 VPN 服务器。VPN 服务器解包，把原始包转发到真正的目的地。

这就是"隧道"——**包中包**。就像把一封信装进另一个信封里寄给一个中转人，中转人拆开外信封，把里面的信再寄给真正的收件人。

## 问题 2：隧道建在哪一层？

VPN 可以在不同层做"包中包"。不同层的 VPN，保护范围不同：

### 二层 VPN（TAP 模式）——在 VPN 之间传以太网帧

```
二层 VPN：
  你的原始数据：[ETH头 | IP头 | TCP头 | HTTP数据]
  整个以太网帧被装进隧道，发到 VPN 服务器
  VPN 服务器收到后，把以太网帧原样注入到它的局域网

效果：
  你的电脑"虚拟地"接在了 VPN 服务器所在的以太网交换机上
  你能收到 VPN 服务器所在局域网的 ARP 广播
  你在 192.168.1.x 网段，VPN 那边的局域网也在 192.168.1.x ← 会冲突

代价：
  额外传输很多无用的广播/组播帧
  效率比三层 VPN 低
```

### 三层 VPN（TUN 模式）——在 VPN 之间传 IP 包

```
三层 VPN：
  你的原始数据：[IP头 | TCP头 | HTTP数据]
  IP 包被装进隧道，发到 VPN 服务器
  VPN 服务器收到后，对 IP 包做路由转发

效果：
  你的电脑"虚拟地"获得一个 VPN 网段的 IP（比如 10.0.0.x）
  你不在 VPN 的局域网里——你是通过路由表访问 VPN 那边的资源
  不传广播帧，高效

WireGuard、OpenVPN TUN 模式、IPsec 都是三层 VPN
```

### 四层及以上（代理 / SOCKS5 / Shadowsocks）

```
代理：
  不是整机流量进隧道，而是单个应用（浏览器）把请求发给代理服务器

  SOCKS5：
    浏览器 → SOCKS5 代理："帮我连接 110.242.68.66:443"
    SOCKS5 → 目标服务器：建立 TCP 连接，中转双方的数据

  这不是 VPN——代理只代理特定应用的流量，VPN 代理整机的流量
```

| | 二层 VPN (TAP) | 三层 VPN (TUN) | 代理 (SOCKS5/HTTP) |
|---|---|---|---|
| 封装的内容 | 以太网帧 | IP 包 | 应用层请求 |
| OSI 层 | 数据链路层 | 网络层 | 传输/应用层 |
| 整机流量 | 是 | 是 | 否（单应用） |
| 广播/ARP 可达 | 是（虚拟在同一局域网） | 否 | 否 |
| 效率 | 低（广播开销） | 高 | 最高 |
| 代表协议 | OpenVPN TAP | WireGuard, OpenVPN TUN, IPsec | Shadowsocks, HTTP Proxy |

> 大多数现代 VPN（WireGuard 等）选择三层（TUN），因为在效率和功能之间达到了最优平衡——不需要虚拟局域网的全部功能，只需要 IP 层可达。

## 问题 3：VPN 怎么加密？——WireGuard 的设计洞见

第四章讲了链路层的 CRC，第六章讲了 TLS 的非对称+对称组合。VPN 面临同样的加密问题：

> A 和 B 需要在不安全的信道上建立一个安全的加密隧道。双方需要交换密钥，然后用对称加密保护后续所有流量。

### 密钥交换：噪声协议框架（Noise Protocol Framework）

WireGuard 不像 TLS 那样在连接时做复杂的算法协商。它的设计哲学是：

> **不协商算法。** 双方预先配置好各自的长久公钥。用 Noise IK 模式在 1-RTT 内完成密钥交换。

```
你的电脑                          VPN 服务器
   │                                  │
   │ 你事先知道服务器的公钥              │ 服务器事先知道你的公钥
   │                                  │
   │──Initiation (1-RTT)───────────→│
   │  用 ECDH 生成临时密钥对          │
   │  用服务器的公钥 + 你的私钥       │
   │    算出共享密钥 S1              │
   │  用 S1 加密第一个数据包          │
   │                                  │
   │←──Response───────────────────│
   │  服务器也生成临时密钥对           │
   │  算出共享密钥 S2                 │
   │  用 S2 加密回复                  │
   │                                  │
   │  此后双方每 2 分钟换一次密钥      │
   │  （无声无息，上层应用完全无感）    │
```

### 加密原语：只用最好的，不协商

WireGuard 没有"加密算法协商"步骤——它**强制使用**一套固定的密码学原语：

```
密钥交换：    Curve25519 ECDH（椭圆曲线 Diffie-Hellman）
对称加密：    ChaCha20 + Poly1305（AEAD——加密 + 认证一体化）
哈希：        BLAKE2s
密钥派生：    HKDF

为什么是 ChaCha20 而不是 AES？
  → AES 需要硬件加速（AES-NI）才快。没有 AES-NI 的 CPU（手机、嵌入式设备）上，
    ChaCha20 比 AES 快得多。
  → Poly1305 是认证标签——不仅加密，还可验证"这个包在传输中没有被篡改"。
```

**为什么要"不协商"？**

TLS 历史上大量漏洞来自算法协商——攻击者诱导双方选一个弱的算法（降级攻击）。WireGuard 说：**如果你不支持 ChaCha20+Poly1305，你就不是 WireGuard 对端，拒绝通信。** 没有协商就没有降级。

### 为什么每 2 分钟换一次密钥？

```
完美前向保密（PFS）：
  → 即使攻击者今天偷到了你的私钥，他也解不开昨天的通信
  → 因为每 2 分钟生成新的临时密钥，旧密钥被立即销毁
  → 每条会话密钥只加密约 100MB 数据就扔掉

换密钥是无声的：
  → 双方在数据包上附带新的临时公钥
  → 收到新公钥后，立即计算新的共享密钥
  → 上层应用完全不知道下面换了密钥
```

## 问题 4：有了隧道，路由表怎么改？

VPN 隧道建好了，但你的电脑默认还是走 Wi-Fi 出去。你必须告诉操作系统：**哪些流量进隧道，哪些不走？**

### 方案一：全隧道（默认路由指向 VPN）

```
路由表：
  0.0.0.0/0 → wg0 接口（VPN 隧道）

效果：
  所有流量都走 VPN
  包括访问百度、微信、游戏、系统更新

代价：
  访问局域网打印机 → 也走 VPN → 到 VPN 服务器后再绕回来 → 不通或极慢
  VPN 服务器在境外 → 国内网站全绕路 → 延迟暴涨
```

### 方案二：分流（策略路由）——"该走的走，不该走的不走"

```
路由表：
  10.0.0.0/24       → wg0（VPN 内网，走隧道）
  192.168.1.0/24     → eth0（家里打印机，直连）
  0.0.0.0/0          → eth0（默认走直连，不经过 VPN）

但你想让某些网站走 VPN：
  → 不能按"目标 IP"静态配置（太多域名、IP 总变）
  → 需要**策略路由**：按进程、按域名、按 IP 集合来决策
  → WireGuard 本身不提供这个，需要配合 iptables/nftables/WireSock
```

**为什么分流这么重要？**

回到第三章的延迟：光速是物理上限。如果你在中国，VPN 服务器在美国：

```
直连百度（北京 → 北京）：       RTT 约 5ms
走 VPN 到美国再回百度：         RTT = 中国到美国(150ms) + 美国回中国(150ms) + 额外处理
                               ≈ 300ms+

访问国内网站走 VPN = 在太平洋上绕了一圈
这是分流之所以重要的物理原因——不是 VPN 慢，是光速不可能更快。
```

## 问题 5：MTU 怎么处理？——加密让包变大了

第五章讲过：链路层 MTU 通常是 1500 字节，超出要分片。

WireGuard 加密一个包时，在外面加了自己的头：

```
原始 IP 包：
  [IP头 20字节 | TCP头 20字节 | 数据 1460字节]
  = 1500 字节（刚好 MTU）

加 WireGuard 隧道头之后：
  [外层IP头 20B | UDP头 8B | WireGuard头 16B | Poly1305认证标签 16B | 加密后的内层IP包 1500B]
  = 1560 字节 → **超过 MTU**

超过 MTU → IP 层必须分片：
  分片 1 发出去，分片 2 发出去
  如果任一片丢了 → 整个原始包作废 → TCP 重传整个包 → 吞吐量断崖式下降
```

**解决方案：调低 MTU**

```
把 VPN 接口的 MTU 设为 1420（留 80 字节给外层头部）

这样：
  上层 TCP 发 1420 字节
  + WireGuard 头 ~60 字节
  + 外层 IP/UDP 头 ~28 字节
  ≈ 1508 字节 ← 但配合 MSS Clamping 可以控制在 1500 以内

MSS Clamping：
  TCP 三次握手时，SYN 包里有 MSS（最大段大小）选项
  防火墙/VPN 截住 SYN，把 MSS 改小
  发方不知道自己被"限段"了——它以为对方宣布的窗口就这么大
  效果：MTU=1420 → MSS≈1380 → TCP 段永远不会超过 1380 → 外层永远不超 MTU
```

## 问题 6：DNS 泄漏——VPN 最常见的漏洞

你的 VPN 开了，所有流量走隧道。但 DNS 呢？

```
没有防泄漏时：
  浏览器：访问 www.baidu.com
  操作系统 DNS：向 192.168.1.1（你的路由器/DNS）发查询
                               ↑
                    这个查询走了 Wi-Fi，没走 VPN 隧道！

  你的 ISP 看到：你在问 "www.baidu.com 的 IP 是什么"
  → 虽然后续 HTTP 流量加密了，但 ISP 已经知道你要访问百度
  → VPN 白开了
```

**防止 DNS 泄漏的方法**：

```
方案 1：让 VPN 服务器也做 DNS 服务器
  连上 VPN 后 → DNS 配置被改为 VPN 服务器的 DNS
  DNS 查询从隧道里走 → ISP 看不到你的 DNS 查询

方案 2：VPN 接口独占 DNS
  绑定 DNS 查询到 VPN 接口（只允许从 wg0 发出 DNS 查询）
  任何从 eth0 发出的 DNS 查询被防火墙拦截

方案 3：本地 DNS 加密（DoH / DoT）
  不依赖系统 DNS → 浏览器直接用 HTTPS 发 DNS 查询给 Cloudflare/Google
  但是：即使 DoH 加密了，你连 Cloudflare 的 IP 也是明的
```

## 问题 7：Kill Switch——隧道断了怎么办？

VPN 隧道基于 UDP，没有"连接"维护。对端可能重启、网络可能断开：

```
你的 VPN 隧道断了（UDP 无状态，你不知道断了）
系统路由表回退到默认 → 所有流量走 Wi-Fi 直连
→ IP 暴露、DNS 暴露、所有流量暴露

VPN 断了的时候你通常不知道——浏览器还在加载，只是慢了
你等了 5 秒才意识到 VPN 断了，而这段时间你的真实 IP 已经泄露了
```

**Kill Switch 做的事情**：

```
VPN 连接活跃时：
  防火墙规则：允许从 wg0 出口的流量；拒绝从 eth0 出口到公网的流量

VPN 连接断开时：
  防火墙规则不变 → eth0 到公网的流量被拒绝
  → 你的所有应用突然"断网"
  → 你知道 VPN 断了（因为网全断了），你可以主动处理
  → 不是静默地在直连中暴露 IP

实现上就是两条防火墙规则（Linux 上 iptables/nftables，Windows 上 WFP，macOS 上 PF）：
  1. 只允许从 wg0 接口出去的流量
  2. 只允许到 VPN 服务器 IP 的流量从 eth0 出去（维持隧道本身）
```

## 问题 8：为什么 WireGuard 比 OpenVPN / IPsec 简单那么多？

这是工程上的一个经典案例。WireGuard 的作者 Jason Donenfeld 的核心洞见：

> **VPN 不需要协议协商。** 双方预先知道对方是谁、用什么算法。

```
OpenVPN 的配置（简化版）：
  选择模式：tun 还是 tap？
  选择协议：UDP 还是 TCP？
  选择加密算法：AES-256-GCM？AES-128-CBC？ChaCha20？
  选择哈希算法：SHA-256？SHA-512？
  选择密钥交换：RSA？ECDHE？
  选择认证方式：证书？预共享密钥？用户名密码？
  选择压缩方式：LZO？LZ4？不压缩？
  ...几十个选项

WireGuard 的配置：
  [Interface]
  PrivateKey = <你的私钥>
  Address = 10.0.0.2/24

  [Peer]
  PublicKey = <服务器的公钥>
  Endpoint = vpn.example.com:51820
  AllowedIPs = 0.0.0.0/0

没有了。没有"选择算法"——算法是固定的。没有"选择模式"——只有三层。
```

**代码量的差异**：

```
OpenVPN：   ~70,000 行代码（用户态）
IPsec：     ~400,000 行代码（内核态 + 用户态）
WireGuard： ~4,000 行代码（内核态）

4,000 行代码意味着：
  → 可以完整审计（一个安全研究人员一天就能看完）
  → 攻击面极小（没有 TLS 那样的算法协商、证书解析、压缩等攻击向量）
  → 可以内置于 Linux 内核（5.6+）
```

## 回到原点

VPN 所有的复杂性，都来自一个简单的事实：

> **你在一个不安全的网络上，但你需要像在自己家里一样安全地访问网络上的资源。**

```
推导链：
  不安全的网络 → 需要加密隧道
  隧道在哪建？→ 三层（TUN）最平衡
  怎么加密？→ 静态配置密钥，不做协商（WireGuard 方案 = 极简 + 最安全）
  包变大了 → MTU 调整 / MSS Clamping
  路由表怎么改？→ 策略路由（该走隧道走隧道，不该走的不走）
  DNS 不能漏 → 强制 DNS 经隧道
  隧道断了 → Kill Switch 阻断所有直连流量

WireGuard 的设计哲学（对照 TLS/HTTPS）：
  TLS：每连接协商一次算法、交换一次密钥
  WireGuard：算法是死的、密钥是预先知道的、隧道无声运行
```

> VPN 不是一个新的"协议层"，它是利用现有各层（IP 封装 + UDP 传输 + 对称/非对称加密）实现的一个**覆盖网络**。它的聪明之处不在于"发明了什么新东西"，而在于**把已有七层的能力重新组合**，解决了各层各自解决不了的问题——"整机流量在不安全网络上的安全传输"。
