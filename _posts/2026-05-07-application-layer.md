# 第七章：应用层

> 传输层已经把可靠的字节流管道建好了。但管道是空的——它不知道里面该装什么、按什么格式装。应用层就是来定义这些的。

---

## 逻辑链总览

```
传输层交给你：两个进程之间，字节流可以可靠地双向流动
  ↓
DNS 要解决的问题
  ├── 问题 1：为什么不用 IP 直接通信？（人记不住 32 位数字）
  ├── 问题 2：为什么不能把全球域名映射存在一台服务器上？（单点故障、不可扩展、无法独立管理）
  ├── 问题 3：既然必须分布式，为什么是层级树而不是扁平表？（逐级授权、独立管理、缓存粒度）
  ├── 问题 4：既然层级查询了，为什么要缓存？（热域名不需要每层都问）
  └── 问题 5：为什么有不同记录类型？（不同的问题需要不同的答案）
  ↓
HTTP 要解决的问题
  ├── 问题 1：TCP 管道是空的，第一条消息该发什么？（请求格式——方法+路径+头部）
  ├── 问题 2：服务器怎么描述"你错了"vs"成功了"vs"搬走了"？（状态码体系）
  └── 问题 3：网页从一张 HTML 变成 50 个资源，TCP 连接怎么用？（版本演进）
  ↓
SMTP 要解决的问题
  └── HTTP 是请求-响应，但收件人可能不在线怎么办？→ 存储-转发模式
  ↓
WebSocket 要解决的问题
  └── HTTP 只能客户端先发，服务器想主动推送怎么办？→ 协议升级为双向通道
  ↓
TLS 要解决的问题
  ├── 问题 1：TCP 字节流是裸奔的，任何人都能偷看 → 需要加密
  ├── 问题 2：对称加密快但密钥分发难，非对称安全但慢 → 两者组合
  └── 问题 3：你怎么知道公钥真的是百度的，不是攻击者伪造的？→ 证书链
```

---

## 问题 0：应用层凭什么存在？

传输层做到了进程之间的可靠字节流。但字节本身不携带含义。

```
TCP 连接建立之后，你可以发任意字节过去。对方的 TCP 也能把字节交到目标进程手里。

但问题是：
  - 服务器跑了几十个服务——这个连接过来，想要什么？（网页？文件？邮件？）
  - 服务器回了 50000 字节——这是成功的网页、404 错误页、还是重定向？
  - 网页引用了 50 张图片——是继续用这条 TCP 连接请求，还是各开各的？

这些全部不在传输层的管理范围之内。传输层只管"送到"，不管"送的是什么"。
```

> 传输层在说："我保证字节能按序无误送到。你来决定送什么字节、怎么解读这些字节。"

应用层就是定义规则的地方：**在这个特定场景下，A 和 B 说什么、按什么格式说、说完了怎么理解对方的意思。**

---

## 第一部分：DNS——从"为什么不直接记 IP？"开始推导

---

### 问题 1：为什么不直接用 IP 地址通信？

上一章网络层已经给全球每台设备分配了层次化 IP 地址，路由器可以找到任何一台主机。理论上，你直接在浏览器输入 `142.250.80.46` 就能访问谷歌。

但人对数字的记忆力极差。`142.250.80.46` vs `google.com`——后者有意义、可联想、能记住。

> 所以 DNS 要解决的第一个问题是：**把人能记住的有意义名字，翻译成机器需要的 IP 地址。**

这是 DNS 存在的全部理由。下面所有的设计——分布式、层次化、缓存、记录类型——都是从这个起点推导出来的。

---

### 问题 2：为什么不把全球的域名→IP 映射存在一台服务器上？

最朴素的方案：搞一台超级服务器，维护全世界所有域名→IP 的映射文件。每个人都来问这台服务器。

**这个方案立刻崩溃，有四个致命问题：**

```
致命问题 1：单点故障
  这台服务器一挂 → 全球互联网"断网"（所有域名无法解析）
  → 虽然 TCP 连接还能用 IP 建立，但没人知道任何网站的 IP

致命问题 2：性能不可扩展
  全球几十亿设备，每秒发出几十亿次 DNS 查询
  一台服务器不可能扛住

致命问题 3：更新无法独立管理
  我注册了一个域名 xiaotuiche.com，想改一下 IP
  → 我得通知这台全球唯一的服务器，等管理员手动更新
  → 百度改 IP 也得排队等 → 不可行

致命问题 4：权威性无法划分
  百度的域名凭什么是百度说了算，不是我替他改的？
  → 一台集中的服务器 = 数据归一个管理员 = 没有"谁拥有什么域名"的概念
```

> 所以 DNS 必须是**分布式的**——由多台服务器共同承担，且每台服务器只管自己有权管的那部分。

---

### 问题 3：既然必须分布式，怎么划分管理边界？

你可以把全世界的域名→IP 映射存成一个大表，然后复制到 1000 台服务器上——但这没有解决核心问题：**谁有权改什么记录？**

正确的思路：**把域名的命名空间按"层级"划分，每一级由不同的组织独立管理。** 这个思路直接导出了 DNS 的层级树：

```
                              ┌───┐
                              │ . │  根域
                              └─┬─┘
                ┌───────────────┼───────────────┐
              ┌─┴─┐          ┌─┴──┐          ┌──┴──┐
              │com│          │ org│          │  cn │  顶级域 (TLD)
              └─┬─┘          └────┘          └──┬──┘
        ┌───────┼────────┐                      │
      ┌─┴───┐ ┌─┴────┐ ┌─┴───┐              ┌──┴───┐
      │baidu│ │google│ │example│             │ com.cn│
      └──┬──┘ └──────┘ └──────┘             └───┬───┘
    ┌────┴────┐                            ┌────┴────┐
  ┌─┴──┐   ┌──┴──┐                      ┌──┴───┐  ┌──┴──┐
  │ www│   │ tieba│                      │ alipay│  │ weibo│
  └────┘   └─────┘                      └──────┘  └─────┘
```

```
www.baidu.com.
│   │     │  │
│   │     │  └── 根域（.）：全球 13 组根服务器，由 ICANN 管理
│   │     └───── 顶级域（.com）：由 Verisign 公司运营
│   └─────────── 二级域（baidu）：百度向 Verisign 注册了 baidu.com
└─────────────── 三级域（www）：百度自己的 DNS 管理员决定
```

**每一级的管理权是独立的：**

```
根域 (.):
  不管 baidu.com 的 IP，只管 ".com 的 DNS 服务器在哪些 IP"
  
.com 顶级域:
  不管 www.baidu.com 的 IP，只管 "baidu.com 由哪些 DNS 服务器管理"
  
baidu.com 权威 DNS:
  百度的管理员决定 www.baidu.com 指向哪个 IP
  没人能替他改——根和 .com 都没有这个权限
```

> 层级结构不是"设计者拍脑袋定的"。它是分布式管理权的必然结果——**谁拥有一个域名，谁就决定它的解析。** 层级树的每个分叉点对应一次管理权限的委托。

---

### 问题 3.1：为什么不干脆用一张扁平表 + 分布式哈希？

这是一个常见的疑问——为什么必须是树？不可以所有域名均匀打散到所有 DNS 服务器上吗？

```
扁平方案：hash("www.baidu.com") → 服务器 42 → 去服务器 42 查

问题：
  → baidu.com 的管理员想给 www.baidu.com 改 IP
  → 他得登录"服务器 42"去改
  → 服务器 42 谁来运维？
  → baidu.com 下的 tieba.baidu.com 散列到了服务器 17
  → 同一个域名的子域名散落在完全不同的服务器上
  → 百度的管理员在改自己域名的 DNS 时，需要接触完全不同的服务器
  → 失去了"管理权"的概念——谁的域名谁管
```

> 层级树的本质是**委托管理模式**，不是一个技术选择。域名空间的每一段被委托给一个组织管理，该组织可以再委托给下一级。这对应的是现实世界的组织层级，不是一种"更好的数据结构"。

---

### 问题 4：既然查询是逐级追溯的，为什么还需要缓存？

从上面的解析流程看，每次查询 `www.baidu.com` 都要从根问到 .com 再问到 baidu.com——三次查询，三次网络往返。全球几十亿次查询，这三台服务器一定被压垮。

> 缓存是这个问题的答案——**每个解析结果都带一个 TTL（存活时间），中间环节记下来，TTL 内不再问。**

DNS 缓存的层级：

```
浏览器缓存（你的 Chrome 记了 10 分钟前查过的 baidu.com）
  ↓ 没命中
操作系统缓存（Windows / macOS 的 DNS 缓存服务）
  ↓ 没命中
本地 DNS 服务器缓存（你的路由器 / 运营商 DNS / 114.114.114.114）
  - baidu.com 这种热门域名，在这里几乎必定命中
  - 本地 DNS 替你把递归查询做完了，把结果记下来
  ↓ TTL 过期
重新递归查询（从根开始）
```

> 缓存使热门域名（baidu.com、google.com）的查询在本地 DNS 服务器就截住了。根服务器最重要、也最"闲"——它只被问到 `.com` 的 DNS 服务器的地址，不是每个域名都要它回答。根服务器负担的真正来源不是百度用户，而是全球几千个顶级域的管理员变更。

---

### 问题 5：为什么有那么多不同的记录类型？

DNS 最核心的是"域名 → IP"的翻译。但其他问题同样需要回答：

```
问题：                  需要回答什么：              记录类型：
网站入口 IP 是多少？      baidu.com → 110.242.68.66   A (IPv4) / AAAA (IPv6)
别名怎么处理？           www.baidu.com 其实就是       CNAME
                        baidu.com 的别名
邮件发到哪？             @baidu.com 的收件服务器        MX（带优先级）
我的 DNS 服务器是谁？    谁回答关于 baidu.com 的查询     NS
附加文本信息？           验证码、反垃圾策略              TXT
```

> 每种记录类型对应一类"域名要回答的问题"——IP 在哪（A）、我是不是别名（CNAME）、邮箱在哪（MX）、谁管我的解析（NS）。没有这些分类，DNS 只能回答一种问题：A 记录。有了分类，DNS 从"电话本"变成了域名的通用信息查询系统。

---

### DNS 回到原点

```
给定：人需要有意义的名字来找到机器。机器需要 32 位数字来建立连接。
问题：找一个系统把前者翻译成后者。

推导：
  一台服务器不可行（单点故障 + 不可扩展 + 无独立管理）
  → 必须分布式
  → 必须按管理权限划分：谁拥有域名，谁管理它的解析
  → 委托制的层级树（根→TLD→权威）
  → 层级查询太多跳 → 必须缓存（TTL）
  → 不同问题需要不同答案 → 多种记录类型

检查：每个设计选择都来自一个约束。"层级"来自管理权委托，"缓存"来自性能，"记录类型"来自问题多样性。不是标准委员会拍脑袋定的。
```

## 第二部分：HTTP——从"TCP 管道是空的"开始推导

---

### 问题 1：TCP 连接建立后，第一条消息发什么？

浏览器已经通过 DNS 拿到百度的 IP，TCP 连接建立。现在这条管道是空的——你可以发任意字节过去。发什么？

百度服务器上可能同时提供网页、文件下载、API 接口。你发的第一条消息必须说清楚：

1. **你想要什么**——哪个文件（`/index.html` 还是 `/search`？）
2. **你想怎么操作**——要看它（GET）、要提交数据（POST）、还是删掉它？
3. **你期望什么格式**——HTML？JSON？图片？

这三个问题直接导出 HTTP 请求的三要素：

```
GET /index.html HTTP/1.1
│    │           │
方法 路径        版本
│    │
│    └── 你要什么资源（哪个路径下的哪个文件）
└─────── 你想怎么操作这个资源
```

**为什么需要"方法"？** 因为同样一个 `/user/123`，不同场景需要不同操作——浏览器想看用户资料（GET），管理员提交表单要修改这个用户（PUT），权限变更可能要删除它（DELETE）。只用路径区分不了操作的意图。

常用方法：

| 方法 | 含义 | 本质区别 |
|---|---|---|
| **GET** | 把这个资源给我 | 只读，不改变服务器状态 |
| **POST** | 把我附的数据交给你处理 | 通常创建新资源，每次请求效果不同 |
| **PUT** | 把我附的数据存到这个路径 | 幂等——发一次和发十次，效果相同 |
| **DELETE** | 删掉这个资源 | 幂等 |
| **HEAD** | 只回头部，不返回内容 | 用于检查资源是否存在、大小多少 |

**为什么需要"路径"？** 服务器不是一个文件——它是成千上万个文件、几百个 API 接口。路径就像文件系统的路径——`/index.html` 是首页，`/images/logo.png` 是图片，`/api/user/123` 是数据接口。没有路径，服务器不知道你想要哪个资源。

**除了方法+路径，还需要什么？——头部**

方法和路径是核心，但不够。你需要额外信息：

```
Host: www.baidu.com            ← "一台服务器托管多个网站，我要访问哪个？"
Accept: text/html              ← "我只能渲染 HTML，别给我 JSON"
Accept-Language: zh-CN         ← "给我中文版"
Connection: keep-alive         ← "用完这条连接别关，我还要其他资源"
User-Agent: Chrome/120         ← "我是什么浏览器（服务器可能给移动版）"
```

**为什么需要 Host？** 因为一个 IP 上可能托管了几百个网站（虚拟主机）。`110.242.68.66` 这个 IP 上可能同时跑着 `baidu.com` 和 `tieba.baidu.com`。TCP 连接只知道 IP，不知道你要访问哪个网站。Host 头告诉服务器"我实际想访问的是哪个域名"。

完整的 HTTP 请求：

```
GET /index.html HTTP/1.1        ← 请求行
Host: www.baidu.com             ←
User-Agent: Mozilla/5.0         ←
Accept: text/html               ←  头部（key: value 格式）
Accept-Language: zh-CN          ←
Connection: keep-alive          ←
                                ← 空行——标志头部结束
                                ← 体（GET 没有体，POST 在这里放表单数据）
```

### 问题 2：服务器怎么描述"你要的东西怎么了"？

客户端发出请求后，可能出现几十种不同的结果——请求成功、资源不存在、你没权限、服务器崩了、资源搬走了。服务器必须用一种**机器可解析的方式**告诉客户端发生了什么。

如果不用数字，服务器只能说"资源不存在"——一个英文句子。客户端解析这个句子做分支逻辑 → 脆弱、不标准、无法扩展。

> HTTP 把这几十种情况编成**三位数字状态码**。第一位数字分大类，后两位细化。

```
1xx：等着，还在处理（很少用）

2xx：成功了
  200 OK              "给你了"
  204 No Content      "成功了但没内容返回"

3xx：你要的东西不在这了
  301 Moved Permanently  "永远搬走了，记住新地址"（浏览器自动更新书签）
  302 Found              "临时搬走了，下次还来问我"
  304 Not Modified       "你上次下载的还没过期，别浪费带宽"（缓存优化）

4xx：你搞错了（客户端的问题）
  400 Bad Request     "你的请求格式我看不懂"
  401 Unauthorized    "先登录"
  403 Forbidden       "登录了也不让看"（没权限）
  404 Not Found       "不存在"

5xx：我搞错了（服务器的问题）
  500 Internal Server Error  "我也不清楚出了什么错"
  502 Bad Gateway            "我问了上游服务，它的回答是错的"
  503 Service Unavailable    "我正在重启 / 扛不住了"
```

> 三位数字的设计意图：第一位让客户端做**策略判断**（2→继续渲染，3→跳转新地址，4→检查自己的请求，5→稍后重试），后两位给**具体信息**。客户端不需要理解每个状态码——它只需要按第一位数字分类处理。

### 问题 3：网页从一张 HTML 变成 50 个资源，TCP 连接该怎么用？

最早的 HTTP/1.0：请求一个 HTML → 收到 → 解析 HTML，发现 50 张图片 → 每张图片开一条新的 TCP 连接（每次都要三次握手）→ 总共 51 条 TCP 连接。

> 约束驱动演进。每一次版本升级，都是在解决上一版本的某个致命瓶颈。

```
HTTP/1.0 → 瓶颈：每请求 = 新 TCP 连接 = 新握手

HTTP/1.1 → 解决：
  加 Connection: keep-alive → TCP 连接用完不断，下一个请求接着用
  新瓶颈：同一连接上同一时间只能有一个请求在飞（队头阻塞）
  50 张图片串行 = 50 个 RTT
  缓解方案：浏览器对同一域名默认开 6 条并行 TCP 连接

HTTP/2 → 解决 HTTP 层的队头阻塞：
  一条 TCP 连接上多路复用 N 个请求（每个有 Stream ID）
  不排队了——服务器交错回复：HTML 的片段、CSS 的片段、图片的片段交替发
  头部压缩（HPACK）：User-Agent 这种长字符串只传一次
  新瓶颈：TCP 层队头阻塞。丢了一个 TCP 段 → 所有流全卡住

HTTP/3 → 解决 TCP 层的队头阻塞：
  不用 TCP，用 QUIC（基于 UDP）
  每个流独立重传：丢了流 3 的包 → 只影响流 3，其他流继续
  0-RTT：连过的服务器，第一个包就可以带加密数据
  内置 TLS 1.3：加密和传输不再是分开的两步
```

| | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|---|
| **传输层** | TCP | TCP | TCP | QUIC (UDP) |
| **每个请求的代价** | 新 TCP 连接（含握手） | 复用连接，串行排队 | 复用连接，多路并发 | 复用连接，多路并发 |
| **队头阻塞在哪** | 连接数爆炸 | HTTP 层 | TCP 层 | 仅影响单流，不跨流阻塞 |
| **加密** | 可选 TLS | 可选 TLS | 强制 TLS 1.2+ | 内置 TLS 1.3 |

> HTTP 版本演进的驱动力不是"想做更好的协议"，而是每一代的瓶颈必然引出下一代的方案。1.0 的瓶颈（每请求一新连接）→ 1.1 的连接复用。1.1 的瓶颈（串行排队）→ HTTP/2 的多路复用。HTTP/2 的瓶颈（TCP 队头阻塞）→ HTTP/3 换 QUIC。**每个版本都在解决上一版本的致命约束。**

## 第三部分：SMTP——从"收件人可能不在线"开始推导

HTTP 的通信模型是**请求-响应**——客户端发起，服务器回应。双方必须同时在线。但电子邮件不是这个模型。

### 问题 1：收件人不在线怎么办？

```
A 发邮件给 B：
  A 写好邮件，点击发送 → 邮件出去了
  B 当时正在飞机上，手机关机 → 三天后才看到这封邮件

如果用 HTTP 的思路：
  A 直接建 TCP 连 B → B 关机 → 连接失败 → 邮件发不出去
```

这个约束是根本性的：**HTTP 假定双方同时在线。邮件不能做这个假定。** 所以邮件需要一个完全不同的通信模型——**存储-转发（Store-and-Forward）**。

### 存储-转发：中间服务器暂存

```
A 的邮件客户端 ──→ A 的发件服务器 ──→ B 的收件服务器 ──→ B 的邮件客户端
    (MUA)            (MSA/MTA)          (MTA/MDA)          (MUA)
    
第 1 跳：A → 发件服务器      SMTP，A 在线即可
第 2 跳：发件服务器 → 收件服务器  SMTP，两台服务器 7×24 在线
第 3 跳：B ← 收件服务器       POP3/IMAP，B 什么时候上线什么时候取
```

A 的发件服务器收到邮件后，它的工作是**找到 B 的收件服务器并转发过去**。如果 B 的收件服务器暂时不可达 → A 的发件服务器把邮件放进队列 → 定时重试 → 最多重试数天。收件服务器收到后存着，等 B 上线来取。

### 问题 2：发件服务器怎么找到收件服务器？

A 写的是 `b@gmail.com`。A 的发件服务器怎么知道 gmail.com 的收件服务器在哪？

答案已经在 DNS 里了——**MX 记录**。

```
A 的发件服务器查 DNS：
  问：gmail.com 的 MX 记录是什么？
  答：gmail-smtp-in.l.google.com，优先级 5
      alt1.gmail-smtp-in.l.google.com，优先级 10
      
  优先级：数字越小越优先。5 不可达时尝试 10。

然后发件服务器建 TCP 连接到 gmail-smtp-in.l.google.com:25
  用 SMTP 协议把邮件"推"过去
```

这就是为什么第七章 DNS 部分要区分 A 记录和 MX 记录——**不同的应用（网页 vs 邮件）需要找到目标主机的不同服务。** 网页找 A/AAAA，邮件找 MX。

### SMTP 与 HTTP 的根本区别

| | HTTP | SMTP |
|---|---|---|
| **通信模型** | 请求-响应（双方在线） | 存储-转发（允许离线） |
| **发起方** | 客户端 | 发件服务器主动推给收件服务器 |
| **消息方向** | 客户端拉（GET）或推（POST） | 全程推（Push） |
| **DNS 依赖** | A/AAAA 记录 | MX 记录 |
| **取信协议** | 无（一次请求就拿到） | POP3/IMAP（收件人从服务器拉取） |

> SMTP 的设计完全由"收件人可能不在线"这一约束驱动。如果邮件通信也是双方同时在线，那 HTTP 就够了——不需要存储-转发，不需要 MX 记录，不需要 POP3/IMAP。SMTP 的存在验证了应用层的核心原则：**不同的通信约束导致完全不同的协议设计。**

## 第四部分：WebSocket——从"服务器也想主动说话"开始推导

HTTP 有一个硬性约束：**必须客户端先发请求，服务器才能回应。** 服务器不能主动给客户端发消息。

```
HTTP 的通信模型：
  Client: "给我 /index.html"  →  Server: "给你"
  Client: "给我 /api/data"    →  Server: "给你"
  
  Server 想主动说"你的订单状态更新了" → 说不出来
  → HTTP 不允许服务器先开口
```

但在很多场景下，服务器确实需要主动推送：股票行情、聊天消息、协作编辑、游戏状态。

### 方案一：轮询（Polling）——最朴素的解法

```
客户端每 5 秒发一个 HTTP 请求："有新消息吗？"
  没有 → 服务器回"没有"
  有   → 服务器回新消息

代价：
  99% 的请求回复是"没有" → 带宽和 CPU 全部浪费
  消息可能等 5 秒才推到 → 延迟不可控
```

这是用 HTTP 模拟推送——本质还是客户端拉，只是假装在推。

### 方案二：长轮询（Long Polling）

```
客户端发 HTTP 请求："有新消息吗？"
  没有 → 服务器不回复，hold 住连接，一直等
  有消息了 → 服务器回复 → 客户端收到 → 立即再发一个新请求

比轮询好：消息零延迟。但：
  每个"hold"消耗服务器一个 TCP 连接
  几千个客户端 = 几千个 hold 住的连接 → 服务器扛不住
```

### 方案三：WebSocket——从 HTTP 升级为双向通道

长轮询的本质问题是**拿请求-响应协议模拟推送**。WebSocket 说：别模拟了，直接在 TCP 之上建一个真正的双向通道。

```
HTTP 握手（升级）：
  Client → Server:
    GET /chat HTTP/1.1
    Upgrade: websocket
    Connection: Upgrade
    
  Server → Client:
    HTTP/1.1 101 Switching Protocols
    Upgrade: websocket
    Connection: Upgrade
    
  此后：TCP 连接还在，但不再走 HTTP 协议
  双方可以随时发消息（帧），不需要等对方先开口
```

WebSocket 本质上做了一件事：**用一次 HTTP 握手建立 TCP 连接，然后拿走这条 TCP 连接的"所有权"，把它从 HTTP 的请求-响应模式切换为全双工消息模式。**

```
HTTP 层：       [HTTP 握手]  ──── 连接升级 ────  后面全是 WebSocket 帧
TCP 层：    [TCP 三次握手] ──────────────────────────────────────→
```

### 为什么 WebSocket 存在——从约束推导

```
约束：HTTP 只能客户端先发，服务器不能主动推送
场景：股票行情、聊天、协作编辑、游戏都需要服务器主动推送

方案：
  轮询        → 浪费带宽，延迟高    → 不行
  长轮询      → 消耗连接，不可扩展  → 不够好
  WebSocket   → 在 TCP 上建立一个真正的双向通道 → 从根上解决问题

WebSocket 不是"额外发明的新协议"——它是 HTTP 的请求-响应约束在特定场景下变得不可接受后的必然产物。
```

## 第五部分：TLS——从"任何人都能偷看"开始推导

---

### 问题 1：TCP 字节流是裸奔的

HTTP 是明文的。任何人只要能抓到你发的 IP 包，就能直接读出你的 HTTP 内容——包括密码。在星巴克连 Wi-Fi，同一个局域网里的任何人都能做到。

> 约束：信道是公开的，任何人都能读取。需求：A 和 B 在这个公开信道上建立一个只有他俩知道的秘密通道。

---

### 问题 2：怎么在不安全的信道上建立一个安全的通道？

两个人在嘈杂的酒吧里，旁边坐满了人。他们想约定一个只有他俩知道的暗号，但周围所有人都能听到他们说话。怎么办？

**对称加密**最快——A 和 B 用同一把密钥加密解密（比如 AES-256-GCM），一条消息加密极快。但问题来了：**怎么在公开信道上安全地交换这把密钥？**

如果 A 直接在信道上说"咱们用密钥 123456"，偷听者也听到了"123456"→ 后续加密全部作废。这是对称加密的密钥分发难题。

**非对称加密**解决了这个问题：

- 公钥加密的 → 只有私钥能解密。公钥可以公开发。
- 私钥签名的 → 公钥可以验证签名。

```
A 拿到 B 的公钥（公开的，谁都能拿）
A 随机生成一把 "会话密钥"
A 用 B 的公钥加密这把会话密钥 → 发给 B
  → 只有 B 有私钥能解密 → B 拿到会话密钥
  → 现在双方有了共享的秘密密钥
  → 后续通信全用这把对称密钥加密（非对称太慢了，不能用来加密大数据）

偷听者拿到了公钥，但没私钥，解不开会话密钥 → 后续对称加密的内容全看不到
```

> 这就是 TLS 的核心设计：**一次非对称加密用来安全地交换对称密钥，后续全部用对称加密进行高速通信。** 两个算法的缺陷互相弥补——对称快但密钥分发难、非对称安全但慢——组合起来就完美了。

---

### 问题 3：你怎么知道那个公钥真的是百度的，不是攻击者的？

TLS 握手中，服务器把它的公钥发给客户端。但一个致命问题立刻出现：

```
攻击者截获你的连接，冒充 baidu.com：
  你 → 攻击者："给我证书和公钥"
  攻击者 → 你："这是我的证书和公钥（伪造的）"
  你用伪造的公钥加密了会话密钥 → 攻击者用自己的私钥解密
  → 攻击者看到了你的密码
  → 攻击者再用百度的真公钥加密，转发给百度
  → 你和百度的通信全程被攻击者透明地中转
```

这就是**中间人攻击**。你要的不仅是加密，还要**身份验证**——"跟我握手的那一方，确实是 baidu.com"。

**证书链是回答这个问题的方案：**

```
浏览器里预装了全球几十个"根 CA"的证书（操作系统更新时维护）

根 CA（DigiCert / Let's Encrypt / GlobalSign）：
  他们的身份不需要验证——浏览器出厂就信任他们
  他们签发"中间 CA"的证书（授权："这个机构可以替我们签发证书"）

中间 CA：
  签发百度的证书："我确认 baidu.com 的管理者拿到的公钥确实是他们的"

百度向中间 CA 申请证书：
  百度生成自己的公私钥对
  把公钥 + "我是 baidu.com" 发给中间 CA
  中间 CA 验证百度真的拥有 baidu.com 的域名（DNS 验证 / 邮件验证）
  验证通过 → 用自己的私钥对百度的证书做签名

浏览器验证证书的过程：
  1. 收到 baidu.com 的证书 → 里面的"签发者"是中间 CA
  2. 用中间 CA 的公钥验证签名 → 有效 → 证书没被篡改
  3. 证书内容写着 CN = baidu.com → 和地址栏一致
  4. 查中间 CA 的证书 → 签发者是根 CA
  5. 用根 CA 的公钥验证 → 有效 → 链是完整的
```

> 整个互联网的信任体系，根节点就是浏览器/操作系统预装的几十个根 CA 证书。篡改任何一环 → 签名验证失败 → 浏览器显示"不安全"警告。证书链不是"额外安全"，它是 TLS 唯一能防止中间人攻击的机制。

---

### TLS 1.3 握手（1-RTT 完成）

```
Client                                    Server
  │                                          │
  │─ClientHello────────────────────────────→│  1.
  │  "我支持的加密算法 + 我的密钥公钥"          │
  │                                          │
  │←─ServerHello + 加密扩展 + Finished───────│  2.
  │  "你选的算法 + 我的密钥公钥 + 证书         │
  │   + 对整个过程签名"                        │
  │                                          │    此时服务器已可发加密数据
  │─Finished───────────────────────────────→│  3.
  │  "收到，验证通过，开始加密通信"             │    此时客户端也可发加密数据
  │                                          │
  │   ←─── 加密数据开始双向传输 ────→         │
```

**为什么 TLS 1.2 需要 2-RTT，TLS 1.3 只要 1-RTT？**

TLS 1.3 去掉了 TLS 1.2 中的两次额外往返：一次是非对称密钥协商（1.3 用了更高效的 ECDHE），一次是双方确认加密算法（1.3 简化了算法协商，客户端在 ClientHello 中就猜服务器会选什么算法）。

**TLS 1.3 0-RTT（PSK 模式）**：如果客户端之前连过这个服务器并缓存了预共享密钥（PSK），那么 TLS 1.3 支持 0-RTT——ClientHello 的第一个包就可以携带加密的应用数据。代价是 0-RTT 数据不提供前向保密，可能被重放攻击（服务器需要额外机制防范）。HTTP/3 的 QUIC 也利用了类似的 0-RTT 机制。

## 一个网页加载的完整时间线

```
0ms     浏览器地址栏输入 www.baidu.com，回车
         │
0ms     DNS 解析
         ├─ 浏览器缓存 → 命中 √ (< 1ms)。如果缓存未命中：
         ├─ hosts 文件 → 可能 0ms
         └─ 递归查询 → RTT 累积 ~50ms
50ms    拿到 IP：110.242.68.66
         │
50ms    TCP 三次握手（1.5 RTT = ~30ms，假设 RTT=20ms）
         │
80ms    TCP 连接建立
         │
80ms    TLS 1.3 握手（1 RTT = ~20ms）
         │
100ms   加密通道建立
         │
100ms   发 HTTP GET /index.html
         │  传播延迟 = 20ms
         │  服务器解析 + 生成 HTML = ~5ms
125ms   收到 200 OK + HTML（约 50KB）
         │
125ms   浏览器解析 HTML，发现引用 50 张图片 + 3 个 CSS + 5 个 JS
         ├─ HTTP/2：同一条 TCP 连接并发请求所有资源
         └─ HTTP/1.1：对同一域名开 6 条并行连接
         │
200ms   关键资源加载完毕，首屏开始渲染
         │
600ms   所有资源全部加载完成
```

每一段的延迟来自不同层：

| 段 | 耗时来源 | 受什么约束 |
|---|---|---|
| DNS | 缓存命中 0，递归查询 10~200ms | 缓存策略、RTT |
| TCP 握手 | 1.5 × RTT | 光速（物理约束） |
| TLS 握手 | 1 × RTT (1.3) | 光速 + 数学运算 |
| HTTP 请求-响应 | 1 RTT (HTML) + N（资源） | 光速 + 服务器处理 |
| 页面渲染 | 浏览器解析、布局、绘制 | CPU/GPU |

> 物理层的光速决定了跨洲最低延迟。网络层的 BGP 决定了路径。传输层的拥塞控制决定了吞吐量。应用层的协议决定了需要几次往返。每个层的延迟都源自那一层的物理或设计约束，层层上叠，构成了用户看到的加载时间。

## 回到原点

应用层所有的协议，都来自一个简单的事实：

> **传输层建立了字节流管道，但它不知道管道里该装什么。**

DNS、HTTP、SMTP、WebSocket、TLS 各自回答了一个"传输层答不了的"问题：

```
DNS：
  约束：人记不住 IP，机器不认识域名。必须有一个翻译系统。
  推导：一台服务器不行 → 分布式。分布式怎么划分 → 委托制 → 层级树。
        层级查询太慢 → 缓存（TTL）。不同问题 → 多种记录类型。

HTTP：
  约束：TCP 管道是空的，双方必须约定"说什么、按什么格式说"。
  推导：必须指定操作意图（方法）、目标资源（路径）。必须告知结果（状态码）。
        网页变复杂 → 连接复用（1.1）→ 多路复用（2）→ 消除 TCP 队头阻塞（3）。

SMTP：
  约束：收件人可能不在线，双方不能假设同时在线。
  推导：必须存储-转发 → 中间服务器暂存 → MX 记录找收件服务器 → POP3/IMAP 取信。

WebSocket：
  约束：HTTP 只能客户端先发，服务器无法主动推送。
  推导：轮询（浪费）→ 长轮询（不可扩展）→ 在 TCP 上建一个真正的双向通道。

TLS：
  约束：TCP 管道是公开的，任何人可偷看。
  推导：需要加密。对称加密快但密钥分发难 → 非对称交换会话密钥。
        公钥可能被伪造 → 需要身份验证 → 证书链（根 CA → 中间 CA → 站点）。
```

> 应用层是分层模型的最后一层。下面六层保证数据"怎么送到"。应用层保证数据"代表什么含义"。用户只看到应用层——地址栏里的 URL、浏览器里的网页、地址栏旁边的小锁。**下面每一层的所有复杂性，对用户透明。这是分层最根本的价值。**
