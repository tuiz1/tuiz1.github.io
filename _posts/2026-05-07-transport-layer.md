# 第六章：传输层

> 网络层把包送到了主机，但主机上有 80 个进程在跑，交给谁？而且网络层不可靠——丢包、乱序、重复，全都不管。传输层就是来解决这些的。

---

## 逻辑链总览

```
网络层交给你：包可以送到目标主机，但不可靠、不到进程
  ↓
问题 1：主机上有 N 个进程，数据交给谁？→ 端口号
  ↓
问题 2：有些场景不需要可靠性，只要快 → UDP
  ↓
问题 3：有些场景需要绝对可靠 → TCP
  ↓
问题 4：TCP 怎么建立连接？→ 三次握手（为什么不是两次？）
  ↓
问题 5：TCP 怎么关闭连接？→ 四次挥手（为什么不是三次？）
  ↓
问题 6：TCP 怎么保证每一个字节都送到？→ 确认 + 重传 + 序号
  ↓
问题 7：发太快了，对方会被淹没 → 流量控制（滑动窗口）
  ↓
问题 8：发太快了，网络中间的路由器也会被淹没 → 拥塞控制
  ↓
问题 9：TCP 连接从生到死经历哪些状态？→ 状态机（11 个状态）
```

---

## 问题 0：传输层凭什么存在？

回顾第五章结尾，网络层有三个它**物理上做不到**的事：

```
缺陷 1：IP 只到主机，不到进程
  你的电脑上有浏览器（进程 A）、微信（进程 B）、游戏（进程 C）
  一个 IP 包到了你的电脑 → 交给谁？
  IP 头里没有"进程标识"

  解决：端口号（16 位整数）。源端口 + 目的端口 → 唯一标识一个连接。

缺陷 2：IP 不可靠
  IP 可以丢包、可以乱序、可以重复
  对于"下载一个文件"来说，丢一个字节整个文件就坏了

  解决：TCP 的确认重传机制——每个字节编号，丢了就重传。

缺陷 3：IP 没有流控
  发送方 10Gbps，接收方只能处理 100Mbps
  IP 层不管——包到了就往上扔
  接收方缓冲区溢出 → 大量丢包 → TCP 重传 → 更拥塞

  解决：TCP 的滑动窗口机制——接收方告诉发送方"我还能收这么多"。
```

## 问题 1：端口号——"这个包是给哪个程序的？"

IP 地址定位到一台主机。但主机上跑了 80 个进程，数据最终要交给哪一个？

**Socket（套接字）= IP 地址 + 端口号**，唯一标识网络上的一次通信端点。

```
192.168.1.5:80     → 这台主机的 Web 服务
192.168.1.5:22     → 这台主机的 SSH 服务
192.168.1.5:54321  → 这台主机上某个临时连接
```

端口号 16 位，0~65535：

```
0 ~ 1023     知名端口（HTTP=80, HTTPS=443, SSH=22, DNS=53）
             操作系统只允许 root 绑定这些端口

1024 ~ 49151  注册端口（MySQL=3306, Redis=6379）

49152 ~ 65535 动态/私有端口
             操作系统临时分配给客户端（你的浏览器访问百度时用的就是这种）
```

你访问百度时发生了什么：

```
你的浏览器：192.168.1.5:45678 → 百度服务器：110.242.68.66:443
                ↑ 临时端口                    ↑ 知名端口

IP 地址找到百度服务器这台主机
端口号 443 找到这台主机上正在监听的 Nginx 进程
```

> 如果说 IP 地址是"大楼地址"，端口号就是"房间号"。邮递员（网络层）把包裹送到大楼门口，传输层负责送到具体的房间。

## 问题 2：UDP——"我不要可靠性，我就要快"

> 无连接、不可靠、面向报文、无拥塞控制。

### UDP 头部（仅 8 字节）

```
┌──────────────────┬──────────────────┐
│  源端口   16bit   │  目的端口  16bit  │
├──────────────────┼──────────────────┤
│   长度    16bit   │  校验和   16bit   │
└──────────────────┴──────────────────┘
```

四个字段。没有序号、没有确认号、没有窗口、没有握手。极简到极致。

### 四个特征的含义

**无连接**：发之前不握手，直接发。应用层给一个数据报，UDP 加上 8 字节头，直接扔给 IP 层。

**不可靠**：不保证送达、不保证顺序。发了三个包，可能只有第 1 和第 3 到了，第 2 永远丢了。UDP 完全不管。

**面向报文**：应用层给什么就发什么，不拆分、不合并。你发 100 字节 → UDP 一个 108 字节的包。你再发 50 字节 → UDP 一个 58 字节的包。**UDP 保留了应用的"消息边界"。**（TCP 没有这个——TCP 面向字节流，会自己决定怎么切。）

**无拥塞控制**：想发多快发多快。网络堵了也不降速。所有 UDP 流加起来可能把网络堵死——这就是为什么有些网络会限 UDP。

### 为什么有了 TCP 还需要 UDP？

第一性原理问：如果 TCP 已经解决了所有可靠性问题，为什么还需要 UDP？

> 因为有些场景**宁愿丢数据也不能等重传**。

```
视频通话：
  丢了 50ms 的音频 → TCP 重传需要 100ms → 用户听到的是 150ms 后的"过时声音"
  → 还不如直接跳过这 50ms，继续播后面的
  → UDP 的"不可靠"在实时场景是"低延迟"

DNS 查询：
  发一个 50 字节的查询 → 丢了就再发一次（应用层重传）
  建立 TCP 连接消耗 1.5 个 RTT（三次握手）→ 然后才发数据
  一个 50 字节的查询不值得建 TCP

在线游戏：
  玩家位置每 50ms 更新一次 → 丢了一个位置包 → 50ms 后有新包
  重传旧位置毫无意义（玩家已经不在那了）
```

> UDP 的存在证明了一个原则：**可靠性不是无代价的。** TCP 的可靠性代价是延迟（重传等待）和开销（三次握手）。当应用宁愿自己处理丢包也不愿承受这个代价时，UDP 就是正确选择。

## 问题 3：TCP——"每一个字节我都要保证送到"

> 面向连接、完全可靠、面向字节流、全双工、拥塞控制。

### TCP 的五个核心特征

```
面向连接：  先三次握手建立连接，再传数据，最后四次挥手关连接
完全可靠：  确认 + 重传，保证按序、无错、不丢、不重
面向字节流：应用给 TCP 的是字节流，TCP 自己决定切多长、什么时候发
全双工：    双方可以同时收发（A 发给 B 的同时，B 也可以发给 A）
拥塞控制：  感知网络拥塞，自动降速，不会把网络堵死
```

### TCP 头部——从"需要什么信息"推导出字段

TCP 要保证可靠传输，必须回答五个问题。每个问题的答案直接对应一个头部字段：

**问题 1：数据交给了哪个进程？** → 源端口 + 目的端口（各 16 位）

跟 UDP 一样——端口号让数据送到正确的进程。IP 只把包送到主机，端口号把数据送到进程。

**问题 2：这个字节是第几个？** → 序号（32 位）

TCP 给**每一个字节**编号，不是给每一个包编号。发方要发 1000 字节，起始序号 1001：覆盖字节 1001~2000，下一段的序号就是 2001。

为什么按字节编号而不是按包编号？因为 TCP 可以自己决定每个段装多少字节。按包编号意味着以后调整段大小会导致编号体系崩溃。按字节编号，不管怎么切，编号都是连续的。

**问题 3：对方收到了哪些字节？** → 确认号（32 位）

确认号 = 期望收到的对方下一个字节的序号。ACK = 2001 表示"字节 1~2000 全部收到，发 2001"。这是**累积确认**——一个 ACK 确认了整段连续数据。

**问题 4：对方还能收多少？** → 窗口（16 位）

ACK 里夹带窗口字段："我的缓冲区还剩这么多"。窗口 = 0 就是"满了，先别发，等我处理完再说"。这是流量控制的核心——发送速率由接收方的处理能力决定。

**问题 5：这个段在连接生命周期的哪一步？** → 6 个标志位

```
SYN：请求建立连接（"我想跟你建立连接"）
ACK：确认号有效。除了第一次握手的 SYN，TCP 所有段都带 ACK
FIN：请求释放连接（"我说完了"）
RST：异常复位（"这连接不对，重来"）
PSH：催上层赶紧读（别在 TCP 缓存里攒着）
URG：紧急数据（几乎不用）
```

这五个问题的答案，加上校验和（跟 UDP 一样要做检错）和首部长度，拼在一起就是 TCP 头部的全部内容：

```
┌──────────────────────────────────────────────────────┐
│  源端口 16b  │  目的端口 16b  │      序号 32b         │
├──────────────────────────────────────────────────────┤
│                    确认号 32b                         │
├──────┬──┬───┬──┬───┬───┬───┬────────────────────────┤
│首部长 │保留│URG│ACK│PSH│RST│SYN│FIN│    窗口 16b     │
├──────┴──┴───┴──┴───┴───┴───┴────────────────────────┤
│  校验和 16b  │  紧急指针 16b  │    选项 (变长)       │
└──────────────────────────────────────────────────────┘
```

> TCP 头部不是设计者随意画的——每个字段都是在回答一个"传输可靠数据必须回答的问题"。**头部的结构 = 传输层职责的信息编码形式。**

## 问题 4：三次握手——建立连接

```
Client                                  Server
  │                                        │
  │───SYN, seq=x────────────────────────→ │ 第 1 次
  │     "我想建立连接，我的起始序号是 x"      │
  │     SYN=1, ACK=0                       │
  │                                        │
  │←──SYN+ACK, seq=y, ack=x+1─────────── │ 第 2 次
  │     "好的，我的起始序号是 y，              │
  │      你下一个字节应该是 x+1"             │
  │     SYN=1, ACK=1                       │
  │                                        │
  │───ACK, seq=x+1, ack=y+1─────────────→ │ 第 3 次
  │     "收到，你下一个字节是 y+1"           │
  │     SYN=0, ACK=1                       │
  │                                        │
  │  连接建立，可以发数据了                  │
```

### 为什么是三次，不是两次？

这是传输层最经典的设计问题。反着想——如果只需要两次握手，会发生什么？

```
两次握手的灾难场景：

1. 客户端发了一个 SYN，seq=x
2. 这个 SYN 在网络里堵了 30 秒（某个路由器队列炸了）
3. 客户端超时了 → 以为丢了 → 又发了一个 SYN，seq=x'
4. 服务器收到新的 SYN → 回 SYN+ACK → 连接建立 → 传数据 → 关连接
5. 然后——那个旧的 SYN（seq=x）终于到了服务器
6. 服务器："哦，有人想跟我建立连接" → 回 SYN+ACK → 分资源，等数据
7. 客户端收到 SYN+ACK（ack=x+1，但客户端根本没发过 x）
   → 客户端："我没想跟你建连接啊" → ???

两次握手：
  服务器收到 SYN 就直接进入 ESTABLISHED 状态，分配资源
  → 那个旧 SYN 骗服务器分配了资源，客户端却不知道
  → 服务器白白浪费资源等一个永远不会来的人

三次握手：
  客户端收到 SYN+ACK 后，确认"我确实想建连接" → 回 ACK
  收到旧 SYN+ACK → 客户端回 RST："我不要"
  → 服务器收到 RST → 释放资源
```

**核心答案**：第三次握手的 ACK 让客户端有机会说"我**确实**想建立这条连接"。如果收到的 SYN+ACK 是过期的、不想要的，客户端可以用 RST 拒绝。这防止了服务器被旧连接请求欺骗而浪费资源。

## 问题 5：四次挥手——关闭连接

```
Client                                  Server
  │                                        │
  │───FIN, seq=u─────────────────────────→ │ 第 1 次
  │     "我说完了，不再发数据了"             │
  │     FIN=1                              │
  │                                        │
  │←──ACK, seq=v, ack=u+1──────────────── │ 第 2 次
  │     "知道了"                            │
  │     ACK=1                              │
  │                                        │
  │   （Server 可能还在发剩余数据...）       │
  │                                        │
  │←──FIN+ACK, seq=w, ack=u+1──────────── │ 第 3 次
  │     "我也说完了"                        │
  │     FIN=1, ACK=1                       │
  │                                        │
  │───ACK, seq=u+1, ack=w+1──────────────→ │ 第 4 次
  │     "知道了，再见"                       │
  │     ACK=1                              │
  │                                        │
  │  等待 2MSL（约 2 分钟）                 │
  │  确保最后的 ACK 没丢                    │
```

### 为什么是四次，不是三次？

因为 TCP 是**全双工**的——每个方向需要独立关闭。

```
客户端发 FIN = "我不发数据了"（半关闭状态：客户端 → 服务器方向已关）
但服务器可能还有数据要发给客户端
  → 服务器不能把 ACK 和自己的 FIN 合在一个包里
  → 先回 ACK（"知道你不发了"）
  → 发完剩余数据
  → 再发 FIN（"我也不发了"）

所以必须分开：
  第 2 次：ACK（确认你的 FIN）
  第 3 次：我的 FIN（我也不发了）
  这两个不能合并，因为它们发生在不同时刻
```

**特殊情况**：如果双方同时发 FIN（同时关闭），ACK 和 FIN 可以合在一个包里 → 三次就完成。

### 为什么要有 TIME_WAIT？

客户端发了最后一个 ACK 后直接关掉不行吗？

```
最后 ACK 在半路丢了：
  
  服务器没收到最后一个 ACK → 超时重发 FIN
  客户端已经关闭了 → 收到 FIN → 回 RST
  服务器收到 RST → "正常关闭变成了异常关闭"
  → 服务器很困惑

TIME_WAIT（2MSL ≈ 2 分钟）的作用：
  1. 如果服务器重发 FIN → 客户端还能再回 ACK
  2. 确保这个连接的所有残留包在网络中全部消失
     （2MSL ≈ 往返时间 × 2，足够让最后一个 ACK 和对端的超时重发 FIN 都消散）
```

## 问题 6：TCP 怎么保证每一个字节都送到？

### 1. 确认应答（ACK）

收到数据 → 回 ACK。发方超时没收到 ACK → 重传。

### 2. 超时重传（RTO）——动态计算超时时间

RTO 不能是固定值。网络延迟一直在变——局域网 RTT < 1ms，跨国 RTT > 150ms。如果 RTO 固定设 100ms，局域网丢包要等 100ms 才重传（太慢），跨国线路正常 ACK 就要 150ms（太快，会假超时）。

TCP 动态追踪 RTT，自适应计算 RTO：

```
每收到一个 ACK，测量这次交互的 RTT 样本

SRTT（平滑 RTT）   = 0.875 × 旧SRTT + 0.125 × 新RTT样本
RTTVAR（偏差）     = 0.75  × 旧RTTVAR + 0.25 × |SRTT - 新样本|
RTO                = SRTT + 4 × RTTVAR

网稳定 → RTTVAR 小 → RTO ≈ SRTT + 小缓冲
网抖动 → RTTVAR 大 → RTO 自动变大，避免假的超时
```

### 3. 滑动窗口 + 累积确认——不等 ACK，连续发

停等协议：发一帧等一帧，利用率 28%。TCP 不用等。

```
发送窗口的四个区域：

┌──────────────┬──────────────┬────────────┬──────────────┐
│   已发已确认   │  已发未确认    │   可以发    │   不能发      │
└──────────────┴──────────────┴────────────┴──────────────┘
                ↑              ↑            ↑
             SND.UNA         SND.NXT    SND.UNA+窗口大小
            (窗口左边界)     (当前发送点)   (窗口右边界)
```

窗口内的数据可以不等 ACK 直接发。收到一个 ACK → 窗口左边界右移 → 右边露出的新数据也可以发了。

**累积确认**：ACK = 3001 表示"字节 1~3000 全部收到"，不是"只收到了第 3000 个字节"。一个 ACK 号确认了整段连续数据。

```
例：
  发方发了字节 1~1000, 1001~2000, 2001~3000
  收方回了 ACK = 3001 → "1~3000 全收到，发 3001"
  收方回了 ACK = 2001 → "只收到 1~2000，2001 以后没收到"
```

## 问题 7：流量控制——防止接收方被淹没

发送窗口的大小 = min（接收方窗口，拥塞窗口）。其中接收方窗口是**接收方通过 ACK 告诉发送方的**——"我还能收这么多"。

```
接收方在 ACK 里携带窗口字段（16 位）：
  "我的缓冲还剩 10000 字节" → 发方窗口 ≤ 10000
  "我的缓冲还剩 0 字节"     → 发方停发
  
窗口 = 0 时：
  发方不发送数据，但定时发一个 1 字节的"窗口探测"包
  对方 ACK 里带的新窗口 > 0 → 恢复发送
```

流量控制是**接收方驱动**的——不是你能发多快，是对方能收多少。

## 问题 8：拥塞控制——防止网络中间的路由器被淹没

流量控制管的是"对方还有多少缓冲"。拥塞控制管的是"网络中间的路由器还有多少缓冲"。

**发方实际发送窗口 = min（接收方窗口，拥塞窗口 cwnd）**

#### 为什么需要单独的拥塞控制？

```
流量控制说："对方能收 64KB，我可以发 64KB"
但如果路径上某个路由器的缓冲只有 8KB 呢？
  64KB 灌进去 → 路由器缓冲溢出 → 大量丢包
  → 丢的不是自己的连接，是所有经过这个路由器的连接
  → 整个网络被拖垮
```

拥塞控制让发方**自己去推测**网络的承受能力，主动限制发送速率。

#### 四个阶段

```
① 慢开始（Slow Start）：
     初始 cwnd = 1 MSS（典型 1460 字节 ≈ 1 个 TCP 段）
     每收到一个 ACK → cwnd += 1 MSS
     → cwnd 指数增长：1 → 2 → 4 → 8 → 16 → 32 ...
     直到 cwnd >= ssthresh（慢开始门限）
     "慢开始"不是什么慢——它是指数增长的，非常快
     叫"慢"是因为它从 1 个 MSS 开始，而不是一下子灌满窗口

② 拥塞避免（Congestion Avoidance）：
     每过一个 RTT → cwnd += 1 MSS
     → cwnd 线性增长：32 → 33 → 34 → 35 ...
     缓慢地试探网络剩余的容量
     每发现网络能扛住，就多塞一个包进去

③ 快重传（Fast Retransmit）：
     收到 3 个重复 ACK（同一个 ACK 号收到第 4 次了）
     → 说明：丢了 1 个包，但后面的包还在送达（网络没全堵死）
     → 不等超时，立刻重传丢失的段
     → ssthresh = cwnd / 2
     → cwnd = ssthresh
     → 进入快恢复

④ 快恢复（Fast Recovery）：
     cwnd = ssthresh（降一半，不是降回 1）
     进入拥塞避免，线性增长
     
     为什么可以"快恢复"而不是"重新慢开始"？
       → 重复 ACK 说明网络还能传数据（只是丢了一个包）
       → 如果网络全堵死了，根本不会有 ACK 回来
       → 所以不需要从 1 个 MSS 重新开始探测

发生超时（真正的严重拥塞）：
     → 包和 ACK 全消失了
     → ssthresh = cwnd / 2
     → cwnd = 1 MSS
     → 重新慢开始
     超时意味着网络可能发生了严重拥塞，需要从头探测
```

### 拥塞窗口的可视化

```
cwnd
  ↑
32│            ╱
16│          ╱
 8│        ╱                    再次线性涨
 4│      ╱                    ╱
 2│    ╱       丢包,降一半 → ╱
 1│  ╱                    ╱
  └──────────────────────────────→ 时间
    │ 慢开始 │ 拥塞避免  │快恢复│
    (指数)   (线性)     (线性)
```

### 6. 小包问题——Nagle 算法与糊涂窗口综合征

前面讲了 TCP 用滑动窗口让发送方连续发送，用拥塞控制防止淹没网络。但还有一个边界情况：**如果应用层以极小的块写入数据，TCP 会怎样？**

```
应用层：write(1 byte) → write(1 byte) → write(1 byte) → ...
TCP：老老实实每个 1 字节都封装成一个 TCP 段发出去

结果：IP 头 20B + TCP 头 20B + 数据 1B = 41 字节的包
      有效载荷只有 1 字节，效率只有 2.4%
      网上跑的 97.6% 都是头部开销
      
更糟的：接收方每次收到 1 字节，就回一个 ACK
      → 网络中充斥着大量"几乎是空的"包
      → 这叫**糊涂窗口综合征 (Silly Window Syndrome)**
```

问题出在两端：
- **发送方**：应用层 1 字节 1 字节地写，TCP 不等，直接发
- **接收方**：应用层 1 字节 1 字节地读，TCP 缓冲区刚空出 1 字节就宣告窗口=1

**Nagle 算法（发方解决）**：

```
规则：TCP 连接上，任一时刻最多只能有一个"未确认的小段"

具体行为：
  1. 如果发方有数据要发，且之前发的小段已经收到 ACK
     → 立即发送（不管数据多大）
  
  2. 如果发方有数据要发，但之前发的小段还没收到 ACK
     → 先把数据攒着（在发送缓冲区里排队）
     → 直到：收到 ACK，或攒够了 MSS 大小
     → 然后一次性发出去

效果：在"一个 RTT 内"，小数据块被合并成一个大数据段
      避免了"每个 1 字节都是一个独立 TCP 段"的灾难
      
Nagle 默认开启，但在低延迟场景下反而有害：
  游戏、实时交互 → TCP_NODELAY 选项关闭 Nagle
  "哪怕浪费带宽也要立即发"
```

**Clark 方案（收方解决）**：

```
规则：接收方不要宣告"很小的窗口"

具体行为：
  接收方缓冲区空出 1 字节 → 不急着宣告窗口=1
  等到缓冲区空出足够多（至少 1 个 MSS，或缓冲区的一半）
  → 再在 ACK 里宣告新窗口

效果：发送方收不到窗口更新 → 停止发送 → 等接收方攒够空间
      避免了"发方收到窗口=1，发 1 字节，收方又回窗口=0"的死循环
```

> Nagle 算法管的是"发方别一次发太少"，Clark 方案管的是"收方别一次宣告太小窗口"。两边配合，把小块的零散数据合并成完整的大段。**TCP 不仅保证可靠性，还要保证效率**——避免网络上跑着大量"几乎是头部"的包。

## 问题 10：TCP 的硬伤催生了什么？——QUIC

第六章花了大量篇幅讲 TCP 的设计，从三次握手到拥塞控制。但现在反过来问一个问题：**TCP 有哪些东西是物理上改不了的？**

### 硬伤 1：队头阻塞（Head-of-Line Blocking）

TCP 保证字节按序到达。丢了字节 1001~2000 → 即使字节 2001~3000 已经收到了，TCP 也不交给应用层，必须等 1001~2000 重传到达。

```
TCP 视角：字节流必须连续，缺一个就等

应用层收到的：████████████░░░░░░░░░░░░████████████
              已到但被 TCP 扣住 ↑   ↑ 已到且可以交
              
QUIC 的解法：每个流独立重传
  Stream 1: 丢了 → 只阻塞 Stream 1
  Stream 2: 继续往前走
  Stream 3: 继续往前走
  
  应用层：Stream 2 和 3 的数据照收不误，不受 Stream 1 影响
```

这不是 TCP 的"bug"——TCP 的设计目标就是按序交付。但现代网页（一个页面 50+ 个资源）不需要全局有序——图片和 CSS 谁先到谁先用，不需要互相等。

### 硬伤 2：握手延迟

```
TCP + TLS 1.3 建立连接：
  TCP 三次握手：1.5 RTT
  TLS 1.3 握手：1 RTT
  总计：2.5 RTT 后才能发 HTTP 请求

QUIC：
  首次连接：1 RTT（TCP 和 TLS 的握手合二为一）
  重连（0-RTT）：第一个包就可以带加密数据
```

### 硬伤 3：协议僵化（Ossification）

TCP 实现在操作系统内核里。更新 TCP 的行为 → 需要更新内核 → 全球几十亿台设备的内核不可能同步升级 → TCP 的演进几乎停滞。

QUIC 跑在用户态（UDP 之上）。更新 QUIC → 更新应用程序 → 浏览器发新版本即可。这就是为什么 QUIC 可以快速迭代，而 TCP 的改进（如 TCP Fast Open）推广了几十年仍未普及。

### QUIC 做了什么？

```
QUIC = 把 TCP 的可靠性 + TLS 的加密 + HTTP/2 的多路复用，全部实现在 UDP 之上

  应用层：    HTTP/3
  传输层：    QUIC（用户态，基于 UDP）
            ├── 可靠传输（类似 TCP 的 ACK + 重传）
            ├── 加密（内置 TLS 1.3，不再分开）
            ├── 多路复用（类似 HTTP/2 的 Stream，但独立重传）
            └── 连接迁移（用 Connection ID 而非 IP+端口标识连接）
  网络层：    UDP（内核态，极简封装）
```

**连接迁移**是 QUIC 最有洞见的设计之一：TCP 用"源 IP + 源端口 + 目的 IP + 目的端口"四元组标识连接。Wi-Fi 切到 4G → IP 变了 → TCP 连接断开 → 必须重连。QUIC 用 Connection ID（一个随机数）标识连接——IP 变了但 ID 不变 → 连接无缝迁移。

> QUIC 不是一个"更好的 TCP"。它是 TCP 的内核态僵化 + 队头阻塞 + 握手延迟这三个硬伤积累到不可忍受之后，**必然出现的解决方案**。它把 TCP 的可靠性思想拿过来，把 TLS 的加密拿过来，把 HTTP/2 的多路复用拿过来，用 UDP 作为底层载体，在用户态重新实现了一遍。这恰恰印证了第六章的推导：**TCP 的每一个设计选择都有代价，当代价大到一定程度，就有人愿意推倒重来。**

## 回到原点

传输层所有的复杂性，都来自一个简单的事实：

> **网络层只负责把包裹送到大楼，但它不可靠，而且不知道大楼里哪个房间。**

传输层必须做三件网络层做不到的事：

```
1. 端口号 → 把数据送到正确的进程（房间号）
2. TCP → 可靠性：每个字节编号，丢了重传，乱序重排
3. 滑动窗口 → 流量控制（不被对方淹没）+ 拥塞控制（不淹没网络）

UDP 的存在提醒我们：
  可靠性不是免费的。当延迟比丢包更致命时，UDP 就是正确的选择。
```

> 传输层在说："网络层把包送到了主机，我来决定交给哪个进程。如果我选 TCP，我保证每一个字节按序无误到达。如果我选 UDP，我只管发，不管到不到。选哪个？看你要可靠性还是要速度。但下面数据怎么在链路层封装、怎么在网络层路由——我不关心。我管的是端到端。"
